# Repository Guidelines

## Project Structure & Module Organization

Foob contains an M1 prototype for a minimal, keyboard-driven Wayland browser. `foob_architecture_decision.md` defines technical decisions; `foob_development_roadmap.md` defines milestones and acceptance criteria. Start with `docs/README.md`, then read `docs/validation/handoff.md` (current state, rules) and `docs/validation/findings.md` (decisions, findings, ideas) before resuming, and update them in the same commit as your change.

`docs/research/qvu/` contains historical Qt experiments, not current implementation requirements. Local mockups in `design-references/qvu/` are ignored by Git and may be absent from fresh checkouts.

The layout uses `src/` for C code, `tests/fixtures/` for HTML cases, and `tests/benchmark/` for measurement scripts. Start with `src/main.c` and `meson.build`. Modules (`src/`):

- `main.c`: argument check (and `--version`, D-32), the core-dump guard (F-77: core limit 1 for every process, so the kernel aborts any dump, D-41; where 1 cannot work, limit 0 and a non-dumpable foob, and the helpers then rely on the collector honouring their limit, D-42; skipped with `FOOB_DIAGNOSTICS=1`; it runs before the argument is parsed) and startup only.
- `target.[ch]`: the startup-URI allowlist, `foob_target_canonical()`, which returns the form foob loads (ASCII, and one WebKit's parser leaves unchanged, M2-02) or nullptr, `foob_target_from_argument()` (the command line only: a `/`, `./` or `../` argument is a path, relative ones against the kernel's current directory, D-32, D-44), `foob_uri_is_local()` (the single trust decision: `about:blank` and local `file:` are trusted, everything else is untrusted; it reads only scheme and host, so WebKit's reported address need not pass the startup rules, D-45) and `foob_navigation_allowed()` (remote content never navigates to local content; required before any load foob makes on a page's behalf, of which there are none, D-04). GLib and POSIX libc only (no WebKit), unit-tested by `tests/test_target.c`, which also links WebKit to check that WebKit's parser keeps each canonical form.
- `window_title.[ch]`: page title to compositor-visible window title (`<title> — foob`); remote titles are sanitized. GLib only, unit-tested by `tests/test_window_title.c`.
- `diagnostics.[ch]`: redacted logging; it must never print URLs, hosts, titles, error text, cookies or input contents. Its interface takes no text, only foob's events and type names; inside, `log_line()` is the one output, and `tests/check_logging.py` (`meson test`) holds every `%s` to a literal, a table entry or a type or quark name (D-61). The only exception is the on-demand dump decided in D-26 (not built yet): hosts but never paths or queries, written only on the user's key to a `0600` file in the profile.
- `browser.[ch]`: the view lifecycle, one window, all shutdown paths stop one main loop, teardown in dependency order (`foob_diagnostics_free()` cancels the deferred geometry source, so any new idle or timeout source must be cancelled on the same path); signal handlers for close, display loss, web-process death, downloads (cancelled, D-02), permission requests (all denied, F-78) and new windows (ignored, D-04; the unused `foob_navigation_allowed()` is the required check for any load M2-03 makes on a page's behalf). It builds `WPEDisplayWayland` directly, so the `WPE_PLATFORM` environment variable cannot select another backend.
- `exit_status.h`: exit codes. 1 start failed (the Wayland display was unreachable, or core dumps could not be turned off), 2 rejected argument, 3 compositor connection lost, 4 web process died; `tests/check_cli.py` depends on 1 and 2.

Split further as responsibilities emerge (the policy handlers are the next candidate, roadmap M2-03). Tests: `meson test -C build` runs the unit tests, the replay of the stored fuzz inputs, `tests/check_cli.py`, the binary contract `tests/check_binary.py` (hardening, the linked libraries and the banned imports, D-47), the static analysis (clang-tidy with `.clang-tidy`, D-52), the duplication check (jscpd: no copied or renamed block of C or Python in `src/` and `tests/`, D-53) the McCabe complexity (lizard: no function in `src/` over 15, D-51; a long chain of `||` is a list, so it goes into a table) and the lint of the Python and shell scripts (ruff with `ruff.toml`, shellcheck; a new shell script is added to its list in `meson.build`, D-59), the logging ban (`tests/check_logging.py`: output calls only in `main.c` and `diagnostics.c`, D-61), and needs no display. Each source check is skipped (77) where its tool is missing; install them for real results: clang-tidy with clang, `cargo install jscpd`, `uv tool install lizard`, and `ruff` and `shellcheck` from pacman. A test runs only locally installed tools, never a download. On GitHub, `.github/workflows/checks.yml` runs `tests/ci.sh` on every push and pull request in an Arch container with every tool installed: the GCC build's `meson test` must pass with no test skipped, then GCC's analyzer compiles every file with any warning an error (D-60) and a clang build with the sanitizers runs the tests (D-54); the nested suite stays local. At each task commit, where llama.cpp is installed, also look for the same logic written twice in different code (D-55): `llama-server -m <jina-code-embeddings-0.5b F16 GGUF> --embedding --pooling last -ngl 99 -c 8192 -ub 8192 -b 8192 --host 127.0.0.1 --port 8090`, then `jscpd --semantic --kind semantic --semantic-url http://127.0.0.1:8090/v1 --semantic-model jina-code-embeddings-0.5b -f c,python --baseline .jscpd-semantic-baseline.json src tests`; each pair marked `[NEW]` is merged, or added to the baseline (`--update-baseline`) with its reason in D-55. Without llama.cpp, jscpd's own CodeRankEmbed works the same way (`jscpd --semantic-download` once, then the command without `--semantic-url` and `--semantic-model`). Never in `meson test` or CI: it needs a downloaded model, and jina's license is non-commercial. At a milestone review, voyage-code-4 (hosted) is a second opinion through the maintainer's key wrapper (D-55); an agent never reads or prints an API key. `python3 tests/nested_lifecycle.py build/foob [--keep] [scenario ...]` runs lifecycle, title, core-dump, permission, download, crash, new-window and logging-ban scenarios in a disposable nested niri (it opens a window on the desktop, removes its scratch directory after a pass); every scenario should keep a negative control that fails on the pre-fix behaviour. `tests/fuzz/` holds the fuzz targets (D-46): `meson test` replays their stored inputs; for a task commit, build them with `CC=clang meson setup <dir outside the repository> -Dfuzz=true -Db_sanitize=address,undefined -Db_lundef=false` and run each for 5 minutes, `<dir>/fuzz-target -jobs=4 -workers=4 -max_total_time=300 -dict=tests/fuzz/uri.dict <scratch corpus> tests/fuzz/seeds/target` (likewise `fuzz-window_title` with `-max_len=20000`), under `ulimit -c 0`; add each failing input to `tests/fuzz/seeds/` with its fix. At each task commit, also build with `-Db_coverage=true` outside the repository, run `meson test` and `python3 tests/coverage_report.py <dir>`: each untaken branch of `target.c` and `window_title.c` gets a test, is removed, or is a known case listed in D-48. `tests/policy_server.py` serves the policy fixtures for guided checks (`docs/validation/guided-checks-m1-audit.md`); input cannot be synthesized here, so clicks stay guided checks. Milestone audits follow the roadmap's triage rule (under *Scope control*) and record evidence in `docs/validation/`.

## Build, Test, and Development Commands

Meson configures a C23 `debugoptimized` build with warning level 3. Environment checks from milestone M0 include:

```sh
pacman -Q wpewebkit meson ninja pkgconf gcc
pkg-config --modversion wpe-webkit-2.0
pkg-config --modversion wpe-platform-2.0
```

These report installed packages and available API modules; the `2.0` suffix denotes the API namespace, not the engine release.

foob follows the packages Arch currently ships (D-71). Fix no exact version of the engine or of a tool in a plan, an instruction, a script or a test; `meson.build` holds minimum versions only. Read a version with a command and state it in each evidence record. When `pacman -Q wpewebkit` differs from the last recorded version, run `meson test` and the nested suite before other work and record the result in the handoff; compare measurements only within one engine version; a probe result older than the installed engine is read again before code relies on it.

Use `meson setup build` to configure, `meson compile -C build` to build, and `meson test -C build --print-errorlogs` to run registered tests. Launch `./build/foob [URI]`; see README for diagnostics and trusted local fixtures. Python checks use only the standard library and need no environment installation.

## Coding Style & Naming Conventions

Target C23 with GLib/GObject at the WPE integration boundary. Keep application-owned logic in ordinary C and use public WPEPlatform APIs. Use four-space indentation and lowercase function/module names. No formatter is configured; `.clang-tidy` is the C linter (D-52) and `ruff.toml` the Python one (D-59), and `meson test` fails on any finding: a check that does not fit is turned off in that file with its reason, and a deliberate case gets a `NOLINT(check)` on its line. GLib cleanup macros may use documented compiler extensions; do not claim an extension-free build. Use descriptive fixture names such as `viewport.html`.

## Testing Guidelines

No coverage threshold exists. Give each milestone task a repeatable acceptance test. Automate stable behavior and document manual niri resize, focus, scrolling, and shutdown checks. The `tests/benchmark/` scripts open real windows and read `/proc/*/smaps_rollup`, so run them only with desktop interaction available; each run records binary and source SHA256, the git revision and whether the tree is dirty, so commit before measuring and pick a new `--output` path every run. Update validation evidence in the same commit as the change it covers. Record package versions, viewport dimensions, workloads, and total browser process-tree PSS for benchmarks; the under-100-MiB goal must be assessed from the current validation evidence. Interactive checks remain required before Gate A. Never fake keyboard or mouse input (no `ydotool`, `wtype` or similar); a test that needs a real click is a guided check done by the maintainer. In M2, each task's guided rows go into `docs/validation/guided-checks-m2.md` when its code is done and are run on that task's commit (D-33). Open Google Scholar only on purpose, when a check needs it (M2-08), at most once or twice a minute; never in an automated test, script, benchmark, loop or retry, so Google does not block this machine's IP. Use Wikipedia, Semantic Scholar and local fixtures for automated or repeated checks. Track binary size as a quality signal: record the stripped size and `size` per object each milestone and explain growth over about 10%; in M2, record and explain it at each task's commit, and from M2-04 on measure startup time as well (D-35, D-39, D-57). Profile only when a startup number grows beyond its noise: `perf record -e cpu-clock:u -g -- <command>`, with `DEBUGINFOD_URLS=https://debuginfod.archlinux.org` on that command for library function names (D-57).

## Commit & Pull Request Guidelines

Use concise, imperative subjects. Keep changes small and tied to roadmap outcomes, such as `M1-03`. Keep M0/M1 evidence with their implementation commits.

PR descriptions should explain behavior, link relevant tasks, and include validation evidence. Add screenshots when visual behavior changes.

## Architecture & Security Boundaries

Preserve the toolkit-free WPE direction: one view per window, no persistent chrome, and PDFs in an external viewer as the target (M3-04). The only chrome is foob's own line, hidden by default and drawn with fcft and pixman (D-28, D-29); never a toolkit, and never a box inside the page. Keep custom engine packaging separate. Never disable TLS checks or sandbox protections, whether for compatibility, speed or memory, and never commit browser profiles and credentials. Any program foob starts gets an argument vector, never a shell, and never `xdg-open` with page-supplied text (D-31). Treat everything from outside this machine as untrusted (page titles, URLs, responses).

Interim defaults, each a maintainer decision that holds until the roadmap task named replaces it:

- Downloads: no download may start and no file be created without an explicit user decision, so every download is cancelled until M3-03 (D-02).
- New windows: every new-window request is ignored (`window.open()` returns `null`, `target=_blank` links and forms do nothing) and foob loads nothing on a page's behalf, until M2-03, M2-11 and M3-01 (D-04). Its M2 replacement is decided but not built: a real click on a `_blank` link opens a private foob process (D-23).
- Permissions: every permission request is denied (pointer lock included, which WebKit would allow unanswered) until M3-05 decides each one (F-78).
- PDFs: they open inline in the stock PDF.js viewer for now (roadmap M3-04 revisits it if a custom build turns PDF.js off); its save button must still obey the download rule (D-12).
